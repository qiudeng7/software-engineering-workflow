# Contributing

Thank you for contributing. This guide must be adapted with this repository's real commands and conventions before use.

## Before starting

1. Read the relevant issue, including its latest handoff and linked decisions.
2. Confirm the goal, scope, acceptance criteria, and unresolved decisions.
3. Inspect the current branch, commit, worktree, related code, and tests.

For work without an issue, first decide whether its size or risk warrants one. Small, obvious corrections may go directly to a pull request.

## Changes and commits

- Keep each pull request focused on one clear problem.
- Preserve unrelated local changes.
- Follow the repository's branch and commit-message rules.
- Update maintained documentation when public behavior, module boundaries, or development commands change.
- Add or update tests for important behavioral constraints and failure modes.

## Pull requests

Link the task and state whether the pull request is complete or partial. Map acceptance criteria to evidence, identify important implementation choices, disclose unverified behavior, and describe relevant risks or follow-up work.

Use automatic issue-closing syntax only when the merge completes the full task, including any required post-merge acceptance.

## Handoffs

For interrupted or transferred work, add a handoff to the task's primary record using the project's handoff format. Include the exact branch and commit, uncommitted-work location, completed work, verification evidence, findings, rejected approaches with conditions, blockers, and one concrete next step.
