# 使用 Issue 和 Pull Request 管理开发过程

本 skill 记录作者常用的开发协作规范，适合作为项目没有明确规则时的默认方案。它不是要求所有项目统一采用的强制标准。项目已有规范时，使用项目规范，不用本 skill 覆盖或改写它。项目规范只覆盖部分内容时，本 skill 只补充未定义的部分，并向用户说明哪些规则来自项目、哪些使用了作者的默认规范。发现两者冲突时停止套用冲突规则，明确指出差异并请用户决定。

本文档所说的issue 和 pr不一定是 GitHub 的 Issue 和 Pull Request，也可以是其他平台的同类概念。本文档所说的 change 是指一个或一系列 commit。

## Issue 和 PR 的职责边界

- **Issue**：一个 change 的提出、设计结果、以及执行过程中又发现的新问题的记录，总体来讲，issue 覆盖一个 change 的问题背景、问题定义和设计部分。
- **Pull Request**：关联 Issue，记录执行步骤的阶段报告、验证结果，以及实际执行和计划不一致的部分。
- **代码与测试**：当前实现的最终事实。
- **README、架构和用户文档**：最终代码和设计的概要描述，Issue 和pr分别表达了change的设计过程和执行过程，但是文档不应该包含过程，只概括表达当前版本的状态，方便他人快速了解当前版本内容。

需求分析、系统设计和执行流程设计可以紧密关联，因此放在同一个子 skill 中；但记录位置仍遵守上述边界。Issue 给出可执行的定义和计划，PR 报告执行阶段、验证结果和计划偏差，不重复 Issue 已经说明的内容。

## 标题与开头

Issue 和 PR 标题直接说明主要变化，需要避免在标题中填入过多细节，好的标题应当能够让读者低负担的、快速的理解重点

- 反例：`feat(user-console): 模型广场与按用量计费的多模型聊天试用`
  将功能、计费规则和模型切换挤进一个名称，读者需要先解析修饰关系才能找到主要变化。
- 正例：`feat(user-console): 添加模型广场和聊天试用`
  直接说明新增能力，详细规则放到正文。
- 正文开头：用户可以在控制台浏览模型并发起聊天。聊天支持切换模型，调用按现有规则计费。

## Change 分类

下表中，每个类型表示 change 产生的主要原因。是否创建同名标签、标题前缀或自定义 Issue Type，遵循仓库已有约定。

| 类型 | 产生原因 | 当前 skill 的覆盖程度 |
|---|---|---|
| `demand-change` | 现有行为符合原需求，但用户或业务期待已经变化 | 已定义需求分析、系统设计、执行简报和 PR 规范 |
| `feat` | 用户或系统需要此前不存在的新能力 | 已定义需求分析、系统设计、执行简报和 PR 规范 |
| `fix` | 当前行为违反已经确定的预期 | 只定义分类 |
| `refactor` | 调整内部结构，不主动改变外部行为 | 只定义分类 |
| `migration` | 从旧接口、数据、依赖或基础设施迁移到新方案 | 只定义分类 |
| `DX` | 改善开发、测试、调试或贡献者工作流 | 只定义分类 |
| `deployment` | 把确定版本交付到目标环境并确认可用 | 只定义分类 |

当 change 属于 `fix`、`refactor`、`migration`、`DX` 或 `deployment`，并且项目也没有定义对应写法时，必须显式告诉用户：

> 当前 change 归类为 `<类型>`。本 skill 目前只定义了该分类的含义，尚未定义它的 Issue 与 Pull Request 写法，需要你补充希望采用的分析、设计和执行规范。

不要默认套用 `feat` 或 `demand-change` 模板，也不要把尚未定义的写法表述成用户已经接受的规范，本 skill 还在开发中，暂时只提供 feat 和 demand-change 类模板。

## `feat` 与 `demand-change` 类的issue

提交此类 issue 的时候需要逐步进行需求分析、系统设计和执行流程设计，用户逐项确认。

`demand-change` 和 `feat` 两者产生原因不同，但进入分析、设计和执行后的工作过程大致相同。

```text
明确需求 → 交付需求分析 → 交付系统设计 → 设计执行流程 → 在 PR 中执行
```

#### 需求分析

需求分析需要结合用户的实际需求、项目的文档和代码来进行，本skills不约束需求分析的具体方法，但要求分析结果能够让人确认范围、流程、规则、数据和交互。

另外 `demand-change` 还需要回答：

- 原需求和当前行为分别是什么；
- 哪些旧的设计、代码、测试、数据、接口和文档将会受到变更影响；
- 是否需要兼容期、迁移或过渡说明；
- 哪些行为明确保持不变。

当重要问题仍未确认时，停下询问用户，不要用推测填满模板。

| 关注点 | 正面说明 | 反面说明 |
|---|---|---|
| 事实依据 | 结合用户需求、项目文档和代码，区分事实、决定与假设。 | 脱离项目套模板，把推测写成已确认事实。 |
| 需求边界 | 说清用户、场景、目标、范围、非目标和验收结果。 | 只写“增加功能”“体验更好”，或直接用实现方案代替需求。 |
| 流程与规则 | 同时覆盖主流程、异常路径、权限、数据和状态变化。 | 只描述理想成功路径，把边界情况留给实现者猜测。 |
| 交付形式 | 只选择有助于确认需求的图，并用领域语言简洁说明。 | 为凑清单堆图，或用代码和技术术语淹没业务问题。 |

需求分析的交付图通常包括: 

| 需要确认的问题 | 常用交付物 |
|---|---|
| 系统边界和外部参与方是谁 | 系统上下文图 |
| 用户能够完成什么 | 用例图 |
| 业务怎样流转，正常与异常路径是什么 | 业务流程图或泳道图 |
| 功能怎样分组和拆分 | 功能结构图 |
| 有哪些业务对象，它们怎样关联 | 概念 ER 图 |
| 用户、系统和外部参与方怎样协作 | 关键业务时序图 |
| 关键对象有哪些生命周期状态 | 状态图 |
| 页面呈现什么，用户怎样操作 | 线框图或可交互原型 |


简单 change 可以合并或省略不适用的图，但要通俗易懂、言简意赅的说明为什么不需要，不得为了满足清单而虚构。

#### 系统设计

系统设计把“要做什么”落实为“由哪些技术组件实现、怎样协作、怎样部署和怎样保障”

| 关注点 | 正面说明 | 反面说明 |
|---|---|---|
| 需求对应 | 每项设计都能对应已确认需求和验收标准。 | 给出通用架构，却无法说明解决了哪个需求。 |
| 边界与变化 | 区分当前实现和拟议变化，明确组件职责、接口与依赖方向。 | 只写“重构”“解耦”“采用最佳实践”，没有具体边界。 |
| 失败与约束 | 说明关键失败路径，以及兼容、安全、性能、部署和恢复约束。 | 只画成功路径，把风险和非功能要求留到开发阶段。 |
| 可落地性 | 以真实代码和运行环境为依据，明确假设、待决问题和取舍。 | 虚构组件或一次性设计所有细节，使方案无法验证和执行。 |

常见的系统设计交付集合包括：

| 交付物 | 应表达的内容 |
|---|---|
| 系统逻辑架构图 | 表达系统分层、主要技术组件、组件职责和依赖方向。标出本次新增或改变的部分，并区分现有实现与拟议设计。 |
| 模块或组件图 | 进一步展开受影响服务内部的职责边界、允许的依赖方向和主要接口，使贡献者能够判断去哪里修改，以及哪些边界不能破坏。 |
| 关键接口时序图 | 在业务时序的基础上补充实际组件、接口或事件，说明同步与异步调用、成功返回、关键失败、超时、重试、幂等和补偿路径。 |
| 数据架构 | 说明物理表或存储归属、关键字段与约束、缓存、消息和数据流向。若不改变持久化数据，应明确写出数据结构保持不变，而不是画一张不存在变化的图。 |
| 部署与网络拓扑图 | 说明入口、网络边界、运行单元、依赖服务和数据设施之间的关系。只有 change 影响部署、网络、容量、环境差异或发布方式时才需要展开。 |
| 安全与运行保障图 | 对正式运行的系统，说明认证授权、敏感数据边界、审计、日志、指标、链路追踪、告警、备份恢复和容灾关系。没有变化的部分可以引用现有设计，不重复绘制。 |

简单单体 change 可以合并逻辑架构、组件、部署和运行保障视图；跨服务、高并发或高风险 change 应分别表达。最终目标是让人能够判断设计是否技术可实现、可扩展、可运维和可恢复，而不是要求固定数量的图。


#### 执行简报

需求和系统设计确认后，在 Issue 中设计怎样执行这个 change，最后交付一个执行简报作为计划。

1. 拆分出可以单独实现的模块，做成monorepo、独立module、lib、package等形式并搭配可运行demo，并在 Issue 中说明模块边界、依赖关系和接口约束；
2. demo 实现完成后再接入系统中，接入要注意遵循适用的设计模式但不能过度设计；
3. 执行简报是计划，不是进度。不要在 Issue 中维护百分比、逐日流水或已经运行的命令结果。

## PR

Pull Request 关联 Issue，并承载执行步骤的阶段报告、验证结果。Issue 中的执行简报是计划，PR 主要记录和计划不一致的部分，有些细节的不一致可以在 PR 中说明原因和取舍，有些显著超出计划范围的变更需要同步回 Issue 并确认后再继续。

PR 只记录执行阶段的关键事件，关键事件有两种，一种是原计划设计的阶段执行完成，那么给出一个阶段简报，另一种是明显超出计划范围的问题，需要暂停并同步到issue中，然后和用户沟通。

正例从新增能力出发，选择与复杂度匹配的分析和设计交付物，并形成可执行计划。反例只有功能愿望和形容词。

正例见 [demo-feat.md](demo-feat.md)，反例见 [demo-feat-bad.md](demo-feat-bad.md)。

正例按执行步骤提交阶段报告，记录验证结果，并区分实现细节偏差和显著超出计划的变更。反例悄悄扩大范围，也没有可复核的验证结果。

正例见 [demo-pr.md](demo-pr.md)，反例见 [demo-pr-bad.md](demo-pr-bad.md)。
