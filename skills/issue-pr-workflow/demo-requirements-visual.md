# 需求分析图文组织：正例

下面以“添加模型广场和聊天试用”展示正文骨架。图片标记代表实际交付的图片，不是允许最终只留占位文字。示例用于说明阅读顺序与图文分工，不代表某个项目已经确认这些需求。

```markdown
# feat(user-console): 添加模型广场和聊天试用

在用户控制台添加模型广场和聊天试用，面向独立登录用户。
聊天按用量计费；切换模型保留当前页面的文字上下文，不保存历史会话。

## 用户可以做什么

[功能边界图：独立登录用户 → 浏览模型、聊天试用；
聊天试用关联现有充值与账单；临时登录不开放]

第一版仅支持文字，不包含文件、语音和工具调用。

## 从浏览模型到开始聊天

[模型广场线框图 → 选择模型 → 聊天页线框图]

模型信息缺失时不推测补齐。已支持 API、尚未支持聊天的模型，
显示原因并提供 API 文档入口。

## 切换模型后怎样继续

[连续交互图：
用户提问 → 模型 A 回答 → 切换到 B → 再次提问 → 模型 B 回答；
明确标出上下文保留、旧回答归属不变、下一次请求使用 B]

历史文字会随下一次请求发送，可能再次产生输入费用。

## 回答和费用怎样产生

[业务流程图：
发送前校验；通过后发起调用；
生成内容与异步结算分开；
分别展开拒绝、中断、用量缺失和扣款失败路径]

停止生成不等于取消费用。费用以服务端确认结果为准。

## 哪些内容会保留

[数据生命周期图：
当前页面保存文字上下文；
刷新、离页、退出后清除；
调用元数据、用量与账务记录仍保留]

这里的“不保存”不代表外部模型服务承诺零留存。

## 待确认事项

只列前面推演中仍未解决的问题，并指向对应图中的位置。

## 验收标准

按上述场景列出可观察、可判断的结果，不再重复整套需求说明。
```

这条阅读路径是：先知道能做什么，再看到怎样使用，接着理解关键规则，最后确认边界。图承担主要分析，文字只补充不便放进图中的条件与例外。

不同需求应沿着自身的理解路径展开，不照搬这些章节或图种。对于 `demand-change`，通常先展示现状与新期待的差异，再展开改变的流程和保持不变的边界。
