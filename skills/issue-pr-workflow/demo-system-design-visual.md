# 系统设计图文组织示例

这是同一 Issue 下的一条新评论骨架，不替换需求分析。图片标记在实际交付时必须换成真实图片；技术组件与方案应由项目事实及已确认需求推导，不直接照搬。

```markdown
## 系统设计：模型广场和聊天试用

依据本轮确认，试用一律收费，其余范围沿用已确认需求。
拟在现有用户站点和后端增加聊天入口，复用模型网关及结算链路。

### 哪些地方需要改变

[组件图：现有用户站点、后端、网关、账务；
标出新增页面与编排模块、修改的准入与计价、保持不变的外部接口]

补充选定方案相较于主要备选的关键取舍。

### 一次发送怎样穿过系统

[接口时序图：浏览器请求、身份校验、模型准入、上游调用、流式响应；
标出调用标识何时建立，拒绝、重复请求和断连在哪处理]

用短表补充图中放不下的请求字段、响应事件和错误语义。

### 费用如何按正确规则结算

[计价与结算图：请求来源 → 价格快照 → 权威用量 → 幂等扣款；
区分本次试用的新规则与普通 API 的原有规则]

补充不能从图中直接看出的零价、缺失价格或用量冲突处理。

### 哪些状态与数据需要保存

[数据关系与状态图：调用、身份、价格快照、结算记录及唯一约束；
区分仅内存存在的正文与持久元数据，展开重启后的恢复边界]

说明新增数据如何迁移，历史数据与旧调用为什么不受影响。

### 怎样发布并判断方案可用

[运行边界图：浏览器、入口代理、后端、网关及外部服务；
体现凭证边界、超时与取消、日志、上线开关及回退路径]

列出需要验证的关键假设和设计对应的测试，不报告尚未执行的结果。
```

读者沿着“改哪里 → 请求怎样走 → 副作用怎样控制 → 数据怎样保存与恢复 → 怎样安全运行”理解方案。并非所有需求都有计费，不应照搬“费用”章节；应选择当前需求最重要的副作用或风险。

反例是先用长篇文字完整描述所有实现细节，再附一张没有接口、数据约束或异常分支的“前端 → 后端 → 数据库”通用架构图。它既没有帮助判断设计，也没有说明与已确认需求的关系。
