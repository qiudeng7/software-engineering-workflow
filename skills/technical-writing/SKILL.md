# 技术文档写作与审阅

让读者理解技术内容、完成操作或作出判断。作者按读者的理解顺序写作，审阅者通过回答实际问题检验文档，而不只是检查措辞。

## 使用入口

先读取[通用协作规范](../../SKILL.md)，再完整阅读[写作指南](references/writing-guidelines.md)。文档的内容职责和协作流程由对应子 skill 规定，本 skill 负责表达与阅读验证，不重复定义流程。

按任务读取对应规范及问题模板，不必加载所有文档类型：

| 文档 | 内容规范 | 参考问题 |
| --- | --- | --- |
| README | [write-readme](../write-readme/SKILL.md) | [README 问题](references/readme-questions.md) |
| CONTRIBUTING | [write-contributing](../write-contributing/SKILL.md) | [贡献指南问题](references/contributing-questions.md) |
| Issue 及设计评论 | [issue-pr-workflow](../issue-pr-workflow/SKILL.md) | [Issue 分阶段问题](references/issue-questions.md) |
| PR 及阶段报告 | [issue-pr-workflow](../issue-pr-workflow/SKILL.md) | [PR 问题](references/pr-questions.md) |

其他技术文档按目标读者的任务构造问题，不强套上述类型。已在当前任务中完整读取的同一规范无需因相互引用再次加载。作为受委派的审阅者使用时，直接执行审阅，不编辑、不发布、不再委派。

## 写作：先明确读者要完成什么

从用户要求和项目材料确定读者、前置知识、阅读目的，以及读完后应能回答的问题。上下文足够时自行整理；只有影响写作方向的缺口才询问用户。

先按读者理解或操作的顺序安排结构，再展开段落和句子。将真实事实、设计提案、待确认事项和未验证内容区分开。依据适用规范安排示例与图，不把文件清单、历史讨论或所有实现细节提前塞进概述。

完成稿件后先自查结构、信息缺口和事实依据，再处理措辞。更新文档时核对相关行为和链接是否已变化，不因原文存在就默认准确。仅请求审阅时只报告问题，不擅自修改。

## 送审：让问题检验文档

编写或修改项目文档后，在交付用户或发布前，调用一个未参与写作的 subagent。局部修改也提供完整阅读上下文；同一交付的相关文档可以一并审阅。

主 Agent 从对应问题模板选取适用问题，结合本次任务改写为具体问题。问题不是必须填满的清单，也不是正文目录；不要要求需求分析提前回答系统设计，更不要要求 README 包含完整架构。问题应覆盖关键目标与风险，同时允许审阅者发现模板之外的缺口。

例如，“系统怎样处理异常？”过于宽泛，可以改为：“请求已发给上游，进程在收到最终用量前退出，系统怎样处理这次调用及费用？”不要问“为什么使用幂等结算后不会重复扣款？”——这已经预设了实现和答案。

使用无写作对话历史的新上下文（工具支持时不继承父对话）。提供目标读者、合理前置知识、文档用途、完整稿件和图片、适用规范、具体问题，以及允许读取的文档链接。不要提供预期答案、作者对方案的额外解释或未进入交付物的讨论历史。

审阅分成两步，由同一审阅者依次完成即可：

1. **读者测试：** 只凭交付材料及其可访问的文档链接回答问题。写作规范指导评判，不能充当项目事实或替文档补全答案。记录答案和依据后，再进入下一步。
2. **规范与事实核对：** 按写作指南及适用子 skill 检查结构、表达和图文一致性。需要核对时，再提供用户约束、源码或其他事实依据，明确它们属于核对材料；不得倒推为第一步中已经读懂。用户最新要求优先于与之冲突的旧规范。

主 Agent 可同时检查链接、附件和事实，但不能替审阅者作答。稿件变化后指明最新版本，避免审阅旧稿。

### 委派示例

> 请只读审阅这份文档。目标读者是……，已知……，需要完成……。
> 请读取通用协作规范、technical-writing 及本类型的规范和参考问题。稿件与图片位于……，读者可访问的关联文档是……。
> 先只凭这些交付材料回答以下问题：……。每项给出答案和具体依据；不能回答时指出缺口，不猜测补全。
> 再按规范检查模板之外的问题，区分交付前必须修改的问题与可选建议，给出位置、读者影响和修改建议。
> 不编辑、不发布、不再委派。说明实际审阅范围，以及未能访问、运行或预览的内容。

## 审阅：先回答，再解释问题

审阅者对每个问题报告：回答、章节或图中的依据，以及存在的缺口和修改建议。可以简短回答已清楚的问题，把说明集中在有问题的地方。

无法回答时区分原因：信息缺失、术语或指代歧义、图文矛盾、内容难以找到，或问题超出本文职责。范围外的问题不直接判为文档缺陷；应调整问题，或检查是否需要增加指向其他文档的入口。明确列为待确认的业务问题不应通过猜测补成结论。

即使能回答，也要检查是否依赖猜测、难以追踪的索引或不必要的阅读绕路。答案听起来合理不代表正确，主 Agent 还需对照已确认需求与事实核对。

最后区分阻断交付的问题与可选建议，说明原因，不为凑意见制造问题。没有阻断问题可以通过；只读源码、检查图片源结构或阅读命令，不能分别冒充运行测试、渲染检查或命令执行。

## 修改与复核

主 Agent 核实反馈后修改，不机械照改。修正后请同一审阅者读取最新稿件，复核未解决的问题及修改影响；原审阅者不可用时，由另一独立审阅者接手并读取审阅记录。不采纳的意见说明理由。

若修改较大，尤其补充了此前依赖口头说明的内容，可再用新上下文测试关键问题，避免审阅者因记住解释而忽略文档缺口。复核通过并不等于完成新的冷读测试。

无阻断问题后结束，不为可选措辞无限循环。分歧涉及需求、权限或范围变化，或缺少必要依据时，报告具体问题并交给用户决定。审阅不代替用户验收，也不授予发布、提交或 push 权限。

环境没有 subagent 能力时，按相同问题自查，并明确注明未经过独立审阅。受委派的审阅者不再触发送审流程。
