# Issue 分阶段参考问题

先确定当前交付阶段，只使用适用的问题。需求分析不因没有文件名或数据库表就判为不完整；设计评论可引用已确认的需求，不必重新复述历史。

## 需求分析：判断要做什么

- 谁在什么情况下遇到了什么问题？
- 完成改动后，用户能够做什么，关键流程怎样进行？
- 哪些条件会阻止操作，失败时用户看到什么？
- 本次包含哪些行为，哪些不在范围内？
- 怎样判断需求已经满足，还有哪些事项需要确认？
- 对需求变更：旧行为与新行为有什么区别，哪些必须保持不变？

例如，对聊天试用需求问“切换模型后，已有文字和后续上下文怎样处理？”不要问尚未进入设计的具体存储表名。

## 系统设计：判断怎样实现

- 哪些现有组件需要修改，哪些能力需要新增或复用？
- 一次关键请求经过哪些组件，谁校验、调用、持久化和决定成功？
- 核心模块接收什么、返回什么，内部怎样得到结果？
- 重复、并发、超时或中断后会留下什么状态，由谁恢复？
- 数据、权限、凭据和外部副作用的边界在哪里？
- 模块与代码位置怎样对应，如何验证关键约束？
- 如有迁移或部署变化：旧数据和调用怎样过渡，怎样回退？

例如，对模型路由设计问“同一协议存在两条候选路由，而调用方没有指定路由时会发生什么？”不能在问题里补充文档没有交代的默认策略。

## 执行计划：判断怎样推进

- 工作按什么边界拆分，前后依赖是什么？
- 每步产出什么，怎样验证后才能进入下一步？
- 哪些模块可独立验证，什么时候接入现有系统？
- 哪些偏差需要回到 Issue 确认，哪些属于执行阶段处理？

未确认的需求可以作为明确的待决事项；缺少支撑实施的关键决策时，应反馈该缺口，而不是替用户作出决定。计划不需要提供尚未发生的测试结果。
