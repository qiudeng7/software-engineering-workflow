# 编写 CONTRIBUTING

CONTRIBUTING 让第一次参与项目的人知道从哪里领取任务、怎样建立开发环境、修改后运行哪些检查，以及提交时提供什么证据。

使用前读取[通用协作规范](../../SKILL.md)和 [technical-writing 子 skill](../technical-writing/SKILL.md)，按其要求组织表达、选择本类型的参考问题，并在完成写作或修改后进行独立审阅。作为审阅者使用本 skill 时，不再发起审阅；当前任务中已读取的同一规范无需重复加载。

## 开始前确认

写 CONTRIBUTING 之前先检查现有 README、依赖与锁文件、脚本、测试目录、CI 工作流、Git 钩子、Issue/PR 模板和托管平台配置。只写仓库中真实存在的命令与规则；无法确认的内容标记为待确认，不根据常见做法自行发明。

编写或重写前，询问用户希望使用中文、英文、单文件双语，还是中英文分别维护。用户已经指定语言，或只是局部修改现有文件时，沿用已有约定。

还要确认项目接受哪类贡献、主要任务平台、分支与提交规则，以及哪些外部服务是本地开发的必要条件。涉及凭据时只说明获取和注入方式，不写真实密钥。

## 思路总结

- **按一次贡献的顺序组织：** 选择任务 → 准备环境 → 修改 → 验证 → 提交评审。
- **命令必须可以执行：** 写明前置条件、执行目录、适用范围和预期结果。
- **验证要求与改动类型对应：** 不要求所有改动机械运行全部测试，也不能只写“确保测试通过”。
- **区分项目规则和建议：** 分支名、提交格式、审查数量等只有项目确实采用时才写成要求。
- **说明未验证内容怎样披露：** 无法执行的检查要写明原因和影响，不能默认为已通过。
- **链接动态任务记录：** Issue、负责人和进度留在托管平台，CONTRIBUTING 说明如何找到和更新它们。

## 推荐结构

### 贡献前

说明在哪里查找任务、哪些改动需要先开 Issue 或设计讨论、如何认领工作，以及安全问题应通过什么非公开渠道报告。小型修正可以简化流程时，应明确范围。

### 开发环境

写清支持的操作系统或运行时版本、包管理器、依赖服务、安装命令、配置文件来源和启动方式。使用仓库锁文件对应的包管理器，不同时给出互相冲突的安装路径。

### 修改和验证

列出稳定的格式化、Lint、类型检查、单元测试、集成测试、端到端测试和构建命令，并说明何时运行。适合用表格表达：

| 改动类型 | 最低验证要求 |
|---|---|
| 文档 | 文档构建或链接检查 |
| 单模块代码 | 格式、静态检查和相关单元测试 |
| 跨模块行为 | 上述检查及相关集成测试 |
| 用户流程或部署行为 | 上述检查及适用的端到端或运行验证 |

表格只是组织方式，实际命令和分类必须依据项目。测试需要数据库、容器、浏览器或第三方服务时，说明隔离方式和数据影响。

### 提交和 Pull Request

说明项目实际采用的分支、提交消息、签名、变基或合并要求。Pull Request 至少应关联任务，说明改动和重要选择，列出实际运行的验证及未运行项，并更新因本次变更失真的文档。

不要把“PR 已合并”自动等同于部署完成或生产可用。项目还有发布或运行验收时，链接对应流程。

## 与其他记录的边界

- README 面向项目使用者，CONTRIBUTING 面向准备修改项目的人；公共安装说明可以链接复用。
- 架构文档解释模块职责和边界，CONTRIBUTING 只提供修改入口与链接。
- Issue 保存具体任务的目标、状态和交接，CONTRIBUTING 只说明任务流程。
- Pull Request 保存本次变更的实现和验证证据，CONTRIBUTING 规定需要提供哪些信息。
- Code of Conduct、Security Policy 和发布手册存在时直接链接，不在 CONTRIBUTING 中复制全文。

## 示例一：小型代码库

正例按“选择任务 → 本地安装 → 检查命令 → 变更要求 → Pull Request”组织，命令短而完整，并明确不同改动需要哪些证据。

反例只有通用的 fork、建分支和提交步骤，没有项目环境、真实命令、测试范围或评审要求，放到任何仓库都不需要修改。

正例见 [demo-1.md](demo-1.md)，反例见 [demo-1-bad.md](demo-1-bad.md)。

## 示例二：Web 应用

正例明确包管理器、环境配置、前后端入口和按改动范围选择的测试，避免贡献者为文档修正运行全部端到端测试，也避免功能改动漏掉构建和用户流程验证。

反例混用包管理器，只写“运行测试”，没有环境变量、浏览器测试、构建要求或跳过检查的披露方式。

正例见 [demo-2.md](demo-2.md)，反例见 [demo-2-bad.md](demo-2-bad.md)。

## 示例三：后端服务

正例说明依赖服务、测试数据库隔离、迁移变更和接口测试，并为安全问题提供独立入口。

反例没有区分开发与生产数据，没有数据库准备和迁移验证，也没有说明外部依赖或接口变更需要更新什么。

正例见 [demo-3.md](demo-3.md)，反例见 [demo-3-bad.md](demo-3-bad.md)。

## 完成前检查

从全新环境按文档执行关键命令，检查路径、链接、版本和工具名称。确认每条强制规则都能在仓库配置、自动化或维护者约定中找到依据，并删除空章节和重复内容。

最后检查贡献者能否回答：去哪里找任务、怎样启动开发环境、当前改动需要运行什么、失败或无法验证时怎样报告、Pull Request 怎样才具备评审条件。
