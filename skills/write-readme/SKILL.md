# 编写 README

编写、修改或审查 README 时，参考以下思路总结和完整示例。

## 开始写作前：确认语言与文件结构

在编写或重写 README 前，先检查仓库现有 README、文档语言和文件命名，然后询问用户希望采用哪一种方式：

1. 只写中文 README；
2. 只写英文 README；
3. 中英文写在同一个 README 中；
4. 中英文分别放在两个文件中，并以英文为主；
5. 中英文分别放在两个文件中，并以中文为主。

如果用户已经明确指定语言和文件结构，不要重复询问。只做局部修改且不会改变现有语言结构时，保持项目当前约定。

选择单文件双语时，继续确认中文在前还是英文在前，并在文件开头提供语言跳转链接，两个语言版本采用对应的章节结构。

选择双文件时，主语言文件使用项目的默认 README 文件名，另一语言文件使用项目已有的语言后缀约定；项目没有约定时：

- 英文为主：`README.md` + `README.zh-CN.md`；
- 中文为主：`README.md` + `README.en.md`。

两个文件开头互相链接。两种语言应表达相同的项目事实、命令、限制和文档入口；不要让其中一个版本长期成为缺少关键内容的摘要。编写完成后同时检查两份文件中的命令、链接、版本要求和章节对应关系。

## 思路总结

这些示例共同遵循几个原则：

- **首句讲清用途：** 写“做什么、用于什么场景”，少写背景和口号。
- **优先给出最短操作路径：** 环境要求、命令、预期结果应放在一起。
- **边界写具体：** “仅支持 UTF-8”比“兼容性有限”更有用。
- **按需设置章节：** 简单项目无需目录；没有复杂配置，就不设配置章节。
- **为其他文档提供入口：** README 保留项目判断和首次使用所需的信息，详细资料通过带说明的链接引出。
- **让内容可验证：** 命令应能执行，链接应存在，许可证应与仓库实际一致。

## README 与其他文档的边界

README 应让第一次接触项目的人完成三件事：判断项目是否适用、走通最短使用路径、知道下一步去哪里查。它不是整个项目文档的容器。

无论是否拆分其他文档，README 通常保留：

- 项目用途、适用场景和影响判断的关键限制；
- 完成第一次使用所需的环境、安装、配置、命令和预期结果；
- 最常用的一两个示例；
- 会造成数据丢失、安全风险或错误操作的重要提醒；
- 指向其他正式文档的索引。

以下内容变长后，应移到独立文档，在 README 中保留简短说明和入口：

- 完整 API、命令行参数或配置项参考；
- 多环境部署、升级、迁移、备份和故障排查手册；
- 模块结构、依赖方向和设计决策；
- 完整开发流程、测试策略和贡献规范；
- 大量进阶示例、集成方式或平台差异。

### “相关文档”放在哪里

有其他文档时，在 README 中设置 `## 相关文档` 或语义相同的章节。默认放在“快速开始”和最小使用示例之后、详细参考和开发说明之前。这样读者先确认项目能运行，再根据目的选择深入阅读。

如果 README 很短，可以把“相关文档”放在许可证之前。README 已有目录时，可以在目录中列出本页章节，但目录不能替代“相关文档”索引，因为后者需要解释每个外部文档解决什么问题。

每个链接都应说明用途，例如：

```markdown
## 相关文档

- [配置参考](docs/configuration.md)：全部配置项、默认值和覆盖顺序。
- [部署指南](docs/deployment.md)：生产环境部署、升级和回退步骤。
- [架构说明](docs/architecture.md)：模块职责、依赖边界和关键执行链路。
- [贡献指南](CONTRIBUTING.md)：开发环境、测试命令和提交规范。
```

只链接实际存在的文档。不要在 README 和独立文档中维护两份完整说明；README 留下最常用路径和必要边界，细节以链接指向的文档为主要记录。重要警告应同时放在相关操作附近，不能只藏在长文档中。

## 示例一：命令行工具——突出“解决什么问题、怎样运行”

按“用途 → 命令 → 结果 → 边界”展开。先让读者完成一次操作，再说明容易误解的行为；功能简单时，不必单独堆砌功能列表。

反例只写“强大、快速、智能”等评价，没有环境、安装命令、可复制的调用、输入输出和行为边界。读者无法知道怎样运行，也无法判断原文件是否改变、重复如何判定或输出冲突如何处理。

正例见 [demo-1.md](demo-1.md)，反例见 [demo-1-bad.md](demo-1-bad.md)。

## 示例二：代码库——突出“如何接入、输入输出是什么”

按“定位 → 安装 → 最小示例 → 接口约定”展开。用真实形式的输入输出代替“简单易用”等评价，让读者快速判断能否接入自己的代码。

反例没有准确说明库解决的问题，也没有真实安装命令、导入方式、输入输出、API 参数、返回值和边界行为。“灵活、高效、易扩展”不能替代可验证的接口约定。

正例见 [demo-2.md](demo-2.md)，反例见 [demo-2-bad.md](demo-2-bad.md)。

## 示例三：Web 应用——突出“能做什么、如何启动和构建”

按“产品能力 → 数据边界 → 启动 → 构建 → 代码入口”展开。使用者先看到能否满足需求，开发者随后找到运行和修改项目的入口。

反例只宣传产品名称和技术栈，没有说明用户能完成什么、数据保存在哪里，也没有运行环境、安装和启动命令、访问地址、构建产物或代码入口。

正例见 [demo-3.md](demo-3.md)，反例见 [demo-3-bad.md](demo-3-bad.md)。

## 示例四：开发工具类 README

适合命令行工具、构建工具、代码检查工具。重点是让读者理解用途、完成操作，并知道如何处理结果。

先帮助读者判断是否适用，紧接着交代检查范围和暂不支持的能力。先展示默认运行路径，再介绍排除规则、输出格式和 CI；命令后立即解释路径基准。每个章节解决一个问题：“快速开始”负责跑通，“常用选项”负责调整，“CI”负责解释自动化中的结果处理。

较长的命令行参考、CI 平台配置和贡献流程通过“相关文档”引出；README 只保留最常见选项和一条通用 CI 路径。

反例没有区分本地链接和 HTTP 链接，没有环境要求、安装命令和最小运行示例，也没有路径解析基准、选项默认值、输出格式、退出码或 CI 失败条件。

正例见 [demo-4.md](demo-4.md)，反例见 [demo-4-bad.md](demo-4-bad.md)。

## 示例五：后端服务类 README

适合 API 服务、小型业务系统、内部工具。比命令行工具多交代配置、接口约定、数据保存方式和使用限制。

按读者接入服务的顺序安排：了解功能、启动服务、调整配置、调用接口，再处理数据和开发问题。示例负责帮助读者完成一次请求，接口约定集中说明状态码、字段限制和错误格式。配置优先级、相对路径基准、初始化是否清空数据、测试是否影响已有数据库等容易误解的地方要明确说明，限制要写出具体后果。

完整 API、生产部署、数据运维、架构和贡献流程容易让服务 README 迅速变长，应在最小请求示例之后提供文档索引，把完整资料放到各自的主要记录中。

反例没有交代服务适用范围、用户模型和认证边界，也缺少依赖安装、配置、数据库初始化、启动和健康检查命令。接口没有路径、请求响应、状态码和错误格式，数据保存、备份及多实例限制也不明确。

正例见 [demo-5.md](demo-5.md)，反例见 [demo-5-bad.md](demo-5-bad.md)。
